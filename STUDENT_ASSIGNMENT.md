# Практика 2. Инженерный контур: что стоит между вами и продом

## Что будем делать

На занятии мы превратим небольшую Kotlin-функцию в проект с тестами и автоматической проверкой изменений на GitHub.

Разберём, как сформулировать ожидаемое поведение, обнаружить ошибку тестом, исправить её и поручить GitHub запускать проверки после каждого изменения.

IDE и возможность запускать Kotlin у вас уже подготовлены.

## Общая часть занятия

Приложение показывает имя пользователя. Функция `displayName(name: String?): String` должна возвращать обычное имя без изменений, а для `null` — строку `"Гость"`.

| Вход | Ожидаемый результат |
|---|---|
| `"Анна"` | `"Анна"` |
| `null` | `"Гость"` |

Вместе с преподавателем мы:

1. Откроем проект и найдём основной код и тесты.
2. Запустим существующий тест и обсудим, что он проверяет.
3. Добавим новое требование и увидим падающий тест.
4. Выясним, почему сборка на GitHub может проходить, даже если тест падает.
5. Добавим запуск тестов в GitHub Actions.
6. Исправим функцию и получим успешный результат локально и на GitHub.

## Проект для самостоятельной работы

После общей части используйте [готовый шаблон проекта на GitHub](https://github.com/nikitosion/kfd-engineering-loop-practice).

```bash
git clone https://github.com/YOUR-USERNAME/kfd-ivanov.git
cd kfd-ivanov
```

Эти команды одинаковы для Bash и PowerShell. В IDEA выберите **File → Open** и откройте скачанную папку, содержащую `settings.gradle.kts`.

### Как запускать проверки

В IDEA запускайте весь класс `DisplayNameTest` стрелкой рядом с его объявлением.

В терминале PowerShell:

```powershell
.\gradlew.bat assemble
.\gradlew.bat test --rerun-tasks
```

В Bash:

```bash
bash ./gradlew assemble
bash ./gradlew test --rerun-tasks
```

Первая команда собирает основной код. Вторая компилирует и запускает тесты. В исходной базе ожидаются два успешных теста.

## Самостоятельное продолжение

Можно выбрать один маршрут или выполнить оба. Самостоятельное продолжение добровольное.

| Маршрут | Что предстоит сделать |
|---|---|
| A. Доработать отображение имени | Добавить новые требования и реализовать их через тесты |
| B. Сообщение готово к отправке? | Проверить чужую реализацию, самостоятельно найти проблемы и исправить их |

## Маршрут A. Доработать отображение имени

Сделайте отображение имени удобнее:

| Вход | Ожидаемый результат |
|---|---|
| `"Анна"` | `"Анна"` |
| `null` | `"Гость"` |
| `"  Анна  "` | `"Анна"` |
| `""` | `"Гость"` |
| `"   "` | `"Гость"` |

1. По образцу существующих тестов добавьте три отдельных теста на новые случаи. Старые тесты сохраните.
2. Запустите весь класс `DisplayNameTest`. С текущей базовой реализацией два старых теста должны пройти, а три новых — упасть.
3. Сохраните этот этап коммитом и отправьте его на GitHub. Откройте **Actions**, найдите неуспешный запуск и прочитайте причину падения.
4. Исправьте функцию, используя null-safety.
5. Убедитесь, что все пять тестов класса `DisplayNameTest` проходят. Сохраните исправление отдельным коммитом и отправьте его. Проверьте успешный запуск в GitHub Actions.

После добавления тестов:

```bash
git add app/src/test/kotlin/kfd/DisplayNameTest.kt
git commit -m "Add display name requirements"
git push
```

После исправления:

```bash
git add app/src/main/kotlin/kfd/DisplayName.kt
git commit -m "Handle blank and padded names"
git push
```

Маршрут завершён, когда функция выполняет все пять требований, тесты сохранены и проходят локально и в GitHub Actions.

## Маршрут B. Сообщение готово к отправке?

В приложении появилась проверка сообщений перед отправкой. Разработчик написал функцию, добавил тест и передал изменение вам на ревью.

Сборка проходит. Тест зелёный. В описании изменения написано: «Проверка готова».

Ваша задача — проверить это утверждение и исправить обнаруженные проблемы. Маршрут можно выполнить независимо от маршрута A.

### Условия задачи

Функция получает текст из внешнего источника. Иногда источник не передаёт значение.

Отправлять можно только непустое сообщение, длина которого не превышает установленный лимит. По умолчанию лимит составляет 140 символов; вызывающий код может указать другой. Неположительный лимит означает, что отправка недоступна.

Для любого набора аргументов, разрешённого объявлением функции, она должна возвращать решение об отправке.

Длина определяется через `String.length`. Пробелы считаются символами и не удаляются.

### 1. Добавьте исходный код

Работайте в своей копии репозитория.

Создайте файл `app/src/main/kotlin/kfd/MessagePolicy.kt`:

```kotlin
package kfd

fun canSendMessage(
    text: String?,
    maxLength: Int = 140
): Boolean = text!!.isNotEmpty() && text.length < maxLength
```

Создайте файл `app/src/test/kotlin/kfd/MessagePolicyTest.kt`:

```kotlin
package kfd

import org.junit.jupiter.api.Assertions.assertTrue
import org.junit.jupiter.api.Test

class MessagePolicyTest {
    @Test
    fun acceptsShortMessage() {
        assertTrue(canSendMessage("Привет"))
    }
}
```

Запустите все тесты проекта из IDEA или терминала.

В Bash:

```bash
bash ./gradlew test --rerun-tasks
```

В PowerShell:

```powershell
.\gradlew.bat test --rerun-tasks
```

Убедитесь, что тесты проходят. Сохраните исходное изменение:

```bash
git add app/src/main/kotlin/kfd/MessagePolicy.kt app/src/test/kotlin/kfd/MessagePolicyTest.kt
git commit -m "Add initial message policy"
git push
```

### 2. Проверьте утверждение «Проверка готова»

Сопоставьте условия задачи с реализацией. Подберите примеры, которые помогут понять, всегда ли функция ведёт себя правильно.

Добавьте свои тесты. Для каждого примера сначала определите ожидаемый результат по условиям задачи, затем проверьте фактический.

Используйте и вызов с лимитом по умолчанию, и вызов с явно заданным лимитом через именованный аргумент.

Сохраните тесты, обнаруживающие проблемы, **до исправления функции**:

```bash
git add app/src/test/kotlin/kfd/MessagePolicyTest.kt
git commit -m "Test message policy requirements"
git push
```

На GitHub откройте **Actions**, найдите запуск для этого коммита и прочитайте причину падения тестов.

### 3. Исправьте функцию

Используйте материал первого занятия. Сохраните имя функции, имена и типы параметров, значение лимита по умолчанию и возвращаемый тип.

Сохраните исходный тест и добавленные вами тесты. Если тест обнаружил ошибку в функции, не удаляйте его и не меняйте ожидаемый результат только ради успешного запуска.

Запустите все тесты проекта. Когда они пройдут, сохраните исправление:

```bash
git add app/src/main/kotlin/kfd/MessagePolicy.kt app/src/test/kotlin/kfd/MessagePolicyTest.kt
git commit -m "Fix message policy"
git push
```

Убедитесь, что сборка и тесты проходят в GitHub Actions. Готовый workflow уже находится в шаблоне; менять его для этого маршрута не требуется.

### Подсказки и самопроверка

> **Не открывайте все подсказки сразу.** Если вы застряли или уже решили задачу и хотите проверить себя, откройте первую подсказку. Попробуйте применить её: добавьте пример, запустите тесты, при необходимости измените код. Только после этого переходите к следующей. Если исправления не нужны, убедитесь, что ваши тесты уже проверяют описанный случай. Использование подсказок — нормальная часть работы.

<details>
<summary>Подсказка 1. Что обещает объявление функции?</summary>

Посмотрите на тип первого параметра. Какие значения он разрешает передать?

Существующий тест проверяет только обычную строку. Подберите другой допустимый аргумент, который поможет проверить обещание: «Функция возвращает решение об отправке».

Сначала запишите ожидаемый результат, затем добавьте тест и запустите его.

</details>

<details>
<summary>Подсказка 2. Разделите входные данные на группы</summary>

Рассмотрите три ситуации:

- Источник не передал значение.
- Источник передал пустую строку.
- Источник передал непустую строку.

Все ли эти ситуации покрыты вашими тестами? Следуют ли ожидаемые результаты из условий задачи?

Для проверки запрета отправки можно использовать `assertFalse`:

```kotlin
import org.junit.jupiter.api.Assertions.assertFalse
```

Если функция вместо результата выбросит исключение, тест тоже завершится неуспешно.

</details>

<details>
<summary>Подсказка 3. Проверьте границу</summary>

Выберите небольшой лимит, например `3`, и проверьте сообщения длиной:

- `2` символа;
- `3` символа;
- `4` символа.

Что означает выражение «не превышает лимит» для каждого из этих случаев?

Задайте лимит именованным аргументом:

```kotlin
canSendMessage(text = "Кот", maxLength = 3)
```

Добавьте отдельные тесты, чтобы по названию упавшего теста было понятно, какое условие нарушено.

</details>

<details>
<summary>Подсказка 4. С чего начать исправление?</summary>

Сначала проверьте, передан ли текст. Если `text == null`, верните `false`: отправлять нечего.

После такого раннего выхода выполнение продолжится только для случая, когда текст есть. Kotlin это учитывает: дальше можно обращаться к `text.length` без `!!`.

Аналогично обработайте недопустимый лимит, затем проверьте остальные условия отправки.

Исправьте реализацию и повторно запустите тесты.

</details>

<details>
<summary>Подсказка 5. Какие требования легко пропустить?</summary>

Отдельно проверьте:

- Нулевой лимит.
- Отрицательный лимит.
- Вызов без аргумента `maxLength`.

Для проверки значения по умолчанию нужны примеры, которые отличают лимит `140` от другого значения. Одной короткой строки недостаточно.

Строку нужной длины можно получить так:

```kotlin
"А".repeat(140)
```

Проверьте сообщение на границе лимита по умолчанию и сообщение на один символ длиннее. В этих вызовах не передавайте `maxLength`.

</details>

### Когда работа завершена

- Функция соответствует условиям задачи.
- Тесты проверяют обычные случаи, особые значения и границы.
- Существующие тесты проекта сохранены и проходят.
- Сборка и тесты в GitHub Actions завершаются успешно.
- Вы можете объяснить, почему исходного зелёного теста было недостаточно.

После публикации общего разбора сравните с ним свой подход и дополните пропущенные проверки. Ваш код не обязан совпадать с эталонной реализацией.
