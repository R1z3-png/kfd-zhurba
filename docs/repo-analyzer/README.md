# Анализатор репозитория

Напишите утилиту на Kotlin, которая получает путь к каталогу и отвечает на два вопроса:
сколько в проекте исходных файлов и строк по каждому расширению и какие три файла самые длинные.
Затем разделите программу на два Gradle-модуля и проверьте, как они пересобираются после правки.

# два обязательных коммита

В истории ветки должны быть два обязательных коммита в таком порядке.

    1. Монолит. Оба отчёта работают в одном Gradle-модуле, тесты проходят. Сделайте коммит до переноса кода.
    2. Модули. Анализатор разделён на :core и :cli. На тех же входных данных вывод прежний, те же тесты проходят. Сделайте отдельный коммит после переноса.

Названия коммитов выберите сами. В отчёте подпишите ссылки на них «Монолит» и «Модули».

# Справка по работе с файлами в Kotlin

| Что нужно сделать                | Как это записать                                                                                                                                           |
|----------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Получить каталог из строки пути  | val root = File(path). Свойство root.isDirectory вернёт false, если путь отсутствует или ведёт к файлу.                                                    |
| Обойти вложенные каталоги        | root.walkTopDown(). Условие в onEnter проверяется до входа в каталог. Если оно вернёт false, вся папка будет пропущена.                                    |
| Найти подходящий файл            | file.isFile проверяет тип, а file.extension даёт расширение без точки. Для build.gradle.kts это "kts".                                                     |
| Распознать символическую ссылку  | Files.isSymbolicLink(file.toPath()). Проверяйте ссылки на каталоги в onEnter, а ссылки на файлы — перед чтением.                                           |
| Посчитать строки                 | file.useLines { lines -> lines.count() } читает UTF-8 и закрывает файл. Для пустого файла результат — 0, для файла с текстом abc без перевода строки — 1.  |
| Получить путь для отчёта         | file.relativeTo(root).invariantSeparatorsPath даст, например, src/A.kt, в том числе на Windows.                                                            |      


# 1. Получите результат в одном модуле

Программа принимает один аргумент — путь к каталогу. Рекурсивно обработайте обычные текстовые файлы с расширениями .kt, .kts и .md. Пропустите каталоги .git, .gradle, build и символические ссылки.

    По расширениям. Для каждого встретившегося расширения выведите число файлов и суммарное число строк. Отсортируйте расширения по алфавиту.
    Три самых длинных файла. Выведите относительный путь и число строк. Сначала идут файлы с бо́льшим числом строк, при равенстве — по относительному пути в алфавитном порядке. Если подходящих файлов меньше трёх, покажите все.

Пустой файл содержит ноль строк. 
Последняя строка с текстом считается и без завершающего перевода строки. 
В пустом каталоге оба отчёта пусты. 
Если путь отсутствует или указывает на файл, выведите понятное сообщение и завершите программу с ненулевым кодом.

# 2. Проверьте себя на четырёх файлах

Создайте этот каталог в тесте или добавьте в проект как пример. 
В таблице \n обозначает перевод строки.

| Путь       | Содержимое                 |
|------------|----------------------------|
| src/A.kt   | package sample\nclass A    |
| src/B.kt   | package sample\nclass B\n  |
| README.md  | Пустой файл                |
| notes.txt  | ignored                    |

Первый отчёт должен дать kt: 2 files, 4 lines и md: 1 file, 0 lines. 
Во втором ожидаются, по порядку, src/A.kt (2), src/B.kt (2), README.md (0). 
Подписи и формат столбцов выберите сами. 
Сохраните тесты на оба отчёта, пустой каталог и ошибку входного пути.

## Запуск на примере из четырёх файлов

Из корня проекта выполните:

```powershell
.\gradlew.bat run --args="core/src/test/resources/repo-analyzer-sample"
```

Пример вывода:

```text
Files and lines by extension:
Extension | Files | Lines
kt | 2 | 4
md | 1 | 0

Three longest files:
File | Lines
src/A.kt | 2
src/B.kt | 2
README.md | 0
```

# 3. Разделите проект и повторите проверку

Перенесите обход файлов, подсчёт и сортировку в :core. 
В :cli оставьте точку входа, аргументы, вывод и код завершения. 
Добавьте зависимость :cli от :core. 
Тесты расчётов должны запускаться в :core без запуска CLI. 
Проверьте теми же тестами, что оба отчёта сохранились. 
Используйте существующий каталог версий проекта для внешних зависимостей.

# 4. Проведите один эксперимент со сборкой

Соберите проект командой ./gradlew build --console=plain 
(в Windows — .\gradlew.bat build --console=plain). 
Выберите небольшую правку внутри реализации :core, 
которая сохраняет публичные сигнатуры и результат программы. 
Например, замените цикл подсчёта на эквивалентную операцию коллекции.

До правки запишите, что ожидаете увидеть у задач
:core:compileKotlin и :cli:compileKotlin. 
Внесите правку, повторите ту же команду без clean и выпишите статусы обеих задач. 
Сопоставьте прогноз с логом и объясните результат в двух-трёх предложениях.
Расхождение с прогнозом допустимо, если вы разобрались, что показал Gradle.

## Результат сборки до правки

В исходной сборке обе задачи компиляции были актуальны:

    > Task :core:compileKotlin UP-TO-DATE
    > Task :cli:compileKotlin UP-TO-DATE

## Прогноз после правки в :core

Ожидаю, что `:core:compileKotlin` выполнится повторно, а `:cli:compileKotlin` останется
`UP-TO-DATE`: изменится реализация внутри `:core`, 
но публичные сигнатуры и результат программы сохранятся.

Правка: в `LineCounter.count` заменено тело с явным `return` 
на expression body; подсчёт по-прежнему выполняется через 
`useLines(Charsets.UTF_8) { it.count() }`. 
Поведение и публичная сигнатура не изменились.

## Результат сборки после правки

После повторного запуска `build --console=plain` получены статусы:

    > Task :core:compileKotlin
    > Task :cli:compileKotlin UP-TO-DATE

Результат совпал с прогнозом: исходник `:core` изменился, 
поэтому его компиляция выполнилась заново. 
Публичный API `:core` не изменился, исходники `:cli` остались прежними, 
поэтому Gradle оставил компиляцию CLI актуальной.
